# Microsoft 365 identity posture (slice 12)

DefendSec reads what a client's Microsoft 365 tenant says about **how easily its accounts could be taken over, and how mail could be hidden or
redirected once one is**. It is read-only, agentless and per client instance: one DefendSec instance reads one tenant, through one app registration
the client's administrator creates. Google Workspace (slice 13) joins the same tables, page and ranking.

This was built after the BEC incident at a client where a mailbox rule moved every QuickBooks/Intuit message into an RSS folder, which hid the
payment-redirection fraud from the owner. A tool that only looks at hosts cannot see that.

## What it reads, and what it never reads

**Reads** (all through Microsoft Graph, all `GET`):

- who has registered a multi-factor method (the authentication methods registration report: a flag and a list of method *types*),
- whether security defaults are on and which Conditional Access policies block legacy sign-in (policy names, states and conditions),
- who holds Global Administrator and a short list of other administrator roles (assignments, not sign-in activity),
- the user list (name, principal name, mail address, enabled, member or guest), to know which mailboxes exist and which domains are the tenant's own,
- the **definition** of each mailbox's inbox rules: the rule's name, its conditions and its actions.

**Never reads**: a message. No body, no subject, no sender of any mail, no attachment. No sign-in log. No file, calendar or chat. The five required
permissions below cannot reach a message. The one optional permission that could (see `Mail.ReadBasic.All`) is **off by default**, DefendSec asks it for
folder *names* only, and a test fails if the collector touches any `/messages` path.

The evidence stored with a finding is the rule definition or the registration flags. A rule's conditions (for instance `senderContains: quickbooks`) are
part of the rule, not of any message.

The only non-`GET` request is the OAuth token request to the login endpoint. `internal/m365/graph` has no method that creates, updates or deletes
anything, and `TestCollectOnlyReadsDefinitionsAndMetadata` records every request of a full read and fails on any method other than `GET`.

## The checks

Findings are of kind `identity`. A check group is **assessed** or **not assessed** as a whole. A group that could not run (a permission missing, a
licence absent, a throttle that did not clear) produces no finding and resolves none: missing evidence is not a pass and not a failure.

| Group | Finding | Severity | Meaning |
| --- | --- | --- | --- |
| MFA registration | `mfa.not_registered` | **critical** Global Administrator, **high** other administrator, **medium** other member user | The account has no MFA method registered. Guests are left out (their own tenant is where they register); disabled accounts are not in the report. |
| Legacy authentication | `legacyauth.not_blocked` | medium | Security defaults are off and no *enabled* Conditional Access policy blocks both legacy client types (`exchangeActiveSync`, `other`) for all users and all applications. A report-only policy is named and does not count. |
| | `legacyauth.partial` | low | A policy blocks some of it (one client type, or a group of users, or some applications). |
| Administrator roles | `roles.global_admin_count` | medium | More direct Global Administrators than the limit (default 4, 1 to 50, set on the Identity page). |
| Inbox rules | `inbox_rule.forward_external` | **high**; **critical** if the rule also deletes, marks read or moves the original, or its conditions match finance words; **low** if the rule is disabled | A rule forwards, redirects or forwards-as-attachment to an address outside the tenant's domains and the trusted domains. |
| | `inbox_rule.hides_mail` | **critical** if its conditions match finance words (invoice, payment, remittance, wire, ACH, bank, QuickBooks, Intuit, payroll, bill.com, purchase order, direct deposit, plus the operator's own); **high** if they match security-notice words (security alert, password, verification code, sign-in, suspicious, unusual activity) or the rule has no condition and deletes or moves everything; **medium** otherwise; **low** if disabled | A rule deletes, permanently deletes, marks as read, or moves mail to a hiding folder (RSS Feeds, RSS Subscriptions, Archive, Conversation History, Deleted Items, Junk Email). |

One finding per rule: a rule that forwards outside *and* hides is one finding, worded and ranked for both.

Words match **whole words**, case-insensitively: `ach` matches "ACH payment", not "reach"; `wire` does not match "wireless". A rule is not a verdict: the
detail says "worth a question to the owner", filing rules are normal, and the fix text starts with "ask the mailbox owner whether they made this rule".

The ranking of identity findings in **Fix this week** follows the surface rules (`internal/exposure/rank.go`): critical and high rank right after KEV
and before every other vulnerability (a stolen password or a forwarding rule needs no exploit), medium and low rank with the vulnerabilities that have
no EPSS score, at the CVSS-equivalent of 5.0 and 2.0. Ties between an identity and a surface finding of the same severity go to the identity one
(`identity:` sorts before `surface:`). These thresholds are a judgement, not measured against a real client list.

### Where the judgement calls are

- **Internal domains** are the domains of the tenant's *member* users' principal names and mail addresses, plus the operator's trusted domains. A guest's
  address is never internal. A tenant with a verified domain that no user uses will see that domain as "outside" until it is added as trusted.
- **Global Administrator** is recognised by role template id `62e90394-69f5-4237-9190-012177145e10` (the GUID Microsoft's own Conditional Access
  examples use for it), or by display name. Other administrator roles are recognised by **display name** (`DefaultPrivilegedRoles`), not GUID, because a
  wrong GUID would be silently wrong; a renamed role falls back to the registration report's own `isAdmin` flag.
- **Folder names** are English. A mailbox that names its folders in another language will not match "RSS Feeds" or "Archive".
- **Legacy authentication** is judged from Entra only. Exchange Online switched Basic authentication off by default for most protocols, and Graph does
  not expose its authentication policies or the SMTP AUTH setting, so the finding says "no Entra-level block was found", and says so in its text.

## What is not assessed (said on every screen)

- Mailbox-level forwarding (`ForwardingSmtpAddress`, `ForwardingAddress`) and transport rules: Exchange Online settings Graph does not expose. Reading them
  needs Exchange Online PowerShell or REST with the `Exchange.ManageAsApp` permission and an Exchange role. **A mailbox forwarded that way does not show here.**
- Roles held through a group (the group is counted, its members are not expanded) and roles that are eligible rather than active (PIM).
- Whether MFA is *enforced*. The registration report says who has a second factor, not whether a policy requires it.
- Exchange Online authentication policies and SMTP AUTH.
- Outlook client-side-only rules (stored in the user's profile, not on the server) and rules outside the inbox.
- Per read: a mailbox that has none (counted), one Graph refused (counted, and its rules are neither confirmed nor cleared), mailboxes past the
  per-read limit of 2,000 (counted as skipped), and the destination folder of a move rule when folder names are off.

Notes on the permissions:

- `MailboxSettings.Read` reads each mailbox's *settings* (rules, automatic replies, time zone). Microsoft documents that an administrator can limit an
  application to specific mailboxes with an Exchange **application access policy**; a mailbox so excluded answers 403, and DefendSec counts it as unreadable.
- **`Mail.ReadBasic.All` is optional and off by default.** Microsoft describes it as "read basic mail properties in all mailboxes... all properties except
  body, previewBody, attachments and any extended properties": that includes the sender and the subject of messages. DefendSec never requests a message,
  and a test enforces it, but the *permission* would let a compromised DefendSec do so. It exists only so a move rule can say "moves it to RSS Feeds"
  instead of "to a folder DefendSec could not name". With it off, a rule that merely marks mail as read or deletes it is still found, and a bare move to an
  unnamed folder is only reported when the rule matches finance words (and then at high, not critical, because the folder may be ordinary). Turn it on only
  if the client agrees, and tick *Name the folder a rule moves mail to* on the Identity page.
- There is no per-user authentication method read (`UserAuthenticationMethod.Read.All`): the registration report answers the question for the whole
  tenant in one paged request. When the tenant has no Entra ID P1 or P2 licence, that report is unavailable and MFA registration is *not assessed*.
  Reading each user's methods instead is a possible later option; it needs one more permission and one request per user.

## Throttling, errors and failing closed

`internal/m365/graph` classifies every failure and the collector turns each into a stated result, never into "clean":

| Answer | What happens |
| --- | --- |
| Token request refused (wrong or expired secret or certificate, unknown app or tenant) | Nothing is read. Every check is *not assessed* with the AADSTS code and Microsoft's first line; the run is recorded as `not_assessed`; no finding is resolved. The secret never appears in the message. |
| `401` from Graph | The token is refreshed once and the request retried; a second `401` is fatal like a refused token. |
| `403` | Not retried. The check that needed it is *not assessed*, with the permission to grant (and the licence, for MFA and Conditional Access). One mailbox answering `403` leaves the rest assessed and that mailbox unread. |
| `404` on a mailbox | The user has no mailbox: counted, not an error. |
| `429` | Waits `Retry-After` (up to 60 s a wait), up to 4 attempts. A longer ask, or a throttle that does not clear, is reported as throttled and the check is *not assessed*. |
| `503`, `504`, `5xx`, network errors | Retried with backoff (1, 2, 4 s), then reported. |
| A `nextLink` to another host | Refused: the bearer token goes only to Graph. Redirects are never followed. |

A run has a budget of 50,000 requests, 4 mailboxes read at a time, 2,000 mailboxes per run and a 30-minute timeout.

## Credentials: files, never the API

Credentials use the same mechanism as the Datto RMM key (`internal/secret`): a **file** named in apid's environment, read each time apid reads the
tenant, so rotating a credential is replacing a file. Nothing secret is typed into the console, stored in a settings table, logged or returned by the API.

| Environment variable | Content |
| --- | --- |
| `DEFENDSEC_M365_CERT_FILE` | A PEM file holding the RSA private key (PKCS #8 or PKCS #1, unencrypted) **and** its certificate. Preferred. Mode 0600; a group- or world-writable file is refused. |
| `DEFENDSEC_M365_SECRET_FILE` | A client secret value, alone in a file, mode 0600. Works, but a secret can be copied and replayed from anywhere. |
| `DEFENDSEC_M365_SCHEDULE=off` | Switches the automatic reads off. |
| `DEFENDSEC_M365_INTERVAL` | How often to read: 1h to 24h, default 6h. |

If both are set the certificate is used (and the status page says so). The status page shows the certificate's SHA-256 thumbprint and days left, so the
operator can match it with the portal; it warns 30 days before expiry and refuses an expired one with a clear message.

The certificate flow is Microsoft's documented client-credentials flow with a signed assertion: header `alg PS256`, `typ JWT`, `x5t#S256`; claims `aud`
(the tenant's token endpoint), `exp` (10 minutes), `iss` and `sub` (the application id), `jti` (unique per request) and `nbf`; posted with
`client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer` (https://learn.microsoft.com/en-us/entra/identity-platform/certificate-credentials).
The tests verify the assertion's signature, thumbprint and claims on a fixture token endpoint and reject a replayed `jti`.

The tenant id and application id are not secrets and are saved in the settings (`m365_settings`), changed only by an administrator, with an
`identity_settings_changed` entry in the hash-chained audit ledger. The tenant must be a directory id or a domain name; `common`, `organizations` and
`consumers` are refused, so one client's data is never read through another's consent.

## Two ways to connect: one app per tenant, or one multi-tenant app for an MSP

**One app per client tenant** (the default; the setup guide below). The client's Global Administrator registers a single-tenant app, uploads a
certificate and grants admin consent. Revoking is deleting the app. Nothing is shared between clients.

**One multi-tenant app for an MSP.** The MSP registers the app once in its own tenant as *Accounts in any organizational directory*, declares the same
five permissions, and uploads its certificate. For each client, that client's Global Administrator opens the tenant-wide admin consent link

`https://login.microsoftonline.com/<client tenant id>/adminconsent?client_id=<application id>`

(https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent) and approves; the app then appears in the client's *Enterprise
applications*, where the client can see its permissions and delete it at any time. The client's DefendSec instance is then configured with **that
client's tenant id** and the **MSP app's application id**, and the MSP's certificate file. The token request goes to the client's tenant endpoint
(never `common`), so the token is for that tenant only. The trade-off: one certificate protects every client, so it needs the care of a master
credential, and an instance's `DEFENDSEC_M365_CERT_FILE` holds a key that could read any consenting tenant if it were pointed at it. DefendSec reads only
the tenant its settings name, and the setting change is in the ledger.

## Setting it up, click by click (administrator)

The same steps are in the console, on the Identity page, under *Connect a Microsoft 365 tenant*.

1. Sign in to **entra.microsoft.com** as a Global Administrator of the client's tenant (granting admin consent needs one). Open **Entra ID > Overview** and copy the **Tenant ID**.
2. **Entra ID > App registrations > New registration.** Name: *DefendSec read-only*. Supported account types: *Accounts in this organizational directory only*. Leave the redirect URI empty. **Register.** On the app's **Overview** page copy the **Application (client) ID**.
3. On the DefendSec server, make a certificate and its bundle:
   `openssl req -x509 -newkey rsa:2048 -nodes -keyout defendsec-m365.key -out defendsec-m365.crt -days 365 -subj "/CN=defendsec-m365"`, then
   `cat defendsec-m365.key defendsec-m365.crt > defendsec-m365.pem` and `chmod 600 defendsec-m365.pem`. In the app: **Certificates & secrets > Certificates > Upload certificate**, and upload the **`.crt` only**. The private key stays on the server. (Alternative: *Client secrets > New client secret*; copy the **Value**, not the Secret ID, at once into a 0600 file.)
4. **API permissions > Add a permission > Microsoft Graph > Application permissions.** Add `AuditLog.Read.All`, `Policy.Read.All`, `RoleManagement.Read.Directory`, `User.Read.All` and `MailboxSettings.Read`. Remove the default delegated `User.Read` (not needed). Click **Grant admin consent for <tenant>** and confirm. Every row must show a green *Granted for <tenant>*.
5. Licences: the MFA report needs Microsoft Entra ID P1 or P2 and Conditional Access needs P1 (Microsoft 365 Business Premium includes P1). Without them those checks say *not assessed*.
6. Set `DEFENDSEC_M365_CERT_FILE=/path/defendsec-m365.pem` for apid and restart it. In the console: **Identity**, enter the Tenant ID and the Application ID, **Connect this tenant**, then **Read the tenant now**.
7. To revoke: delete the app registration (or only its certificate), or **Enterprise applications > the app > Properties > Delete**. Deleting the file on the server stops DefendSec from signing in at all.

## API (apid admin API)

| Route | Who | |
| --- | --- | --- |
| `GET /v1/identity/status` | viewer | settings, credential state (method, thumbprint, expiry; no secret), summary, latest run, what is not assessed, the permission list |
| `PUT /v1/identity/m365/settings` | admin | `tenantId`, `clientId`, `cloud`, `globalAdminMax`, `trustedDomains`, `financeTerms`, `resolveFolders`; unknown fields are refused, so a pasted secret is a `400` |
| `POST /v1/identity/m365/sync` | admin | `{wait?}`: `202` and a background read, or `200` with the run; `409` if one is running |
| `GET /v1/identity/findings?resolved=1&check=` | viewer | |
| `GET /v1/identity/runs?limit=` | viewer | |
| `GET /v1/exposure/advisory?id=identity:<12 digits>` | viewer | the drawer of an identity row |

Every settings change, manual read and recorded run is in the audit ledger (`identity_settings_changed`, `identity_sync`, `identity_run_recorded`);
a run and its ledger entry commit in one transaction.

## What it does not prove

- Findings are **not yet in the signed evidence export** (`defendsec-verify`): the ledger chains each run (which run, its status, how many findings it
  opened and closed) but not the findings themselves. That belongs with scout's evidence hardening (slice 7c).
- "Registered" is not "enforced". "Not found" for a rule means not found in the inbox rules Graph returns, not that the mailbox is clean.
- Reachable is not compromised. A finding says a condition is true of the tenant's configuration; it is evidence to act on, not proof that anyone abused it.
