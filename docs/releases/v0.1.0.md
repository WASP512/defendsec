# DefendSec v0.1.0

The first release of DefendSec as an **exposure-management tool** for small fleets and MSP
clients. One self-hosted instance per client tells you what is exploitable, what is out of date,
what is misconfigured and what is exposed from outside, ranks it **KEV → EPSS → CVSS**, and keeps
evidence that it is getting better.

It is **not an EDR**. The detection and response half was removed; see the
[changelog](https://github.com/WASP512/defendsec/blob/main/CHANGELOG.md) for exactly what went and
what stayed.

## Install

On a Proxmox VE host, as root (creates a Debian 12 container and installs this release in it):

```bash
curl -fL -o create-proxmox-ct.sh \
  https://github.com/WASP512/defendsec/releases/download/v0.1.0/create-proxmox-ct.sh
bash create-proxmox-ct.sh
```

On any Debian, Ubuntu, Fedora, RHEL-family or openSUSE machine, as root:

```bash
curl -fL -o install-server.sh \
  https://github.com/WASP512/defendsec/releases/download/v0.1.0/install-server.sh
bash install-server.sh
```

Both install **this** release from prebuilt, checksummed files; nothing is compiled. They also
start the first vulnerability feed sync and schedule it daily. Then open
`https://<server>:47261` within 30 minutes and create the administrator account, and enroll hosts
from the Enroll page. Full steps: [docs/INSTALL.md](https://github.com/WASP512/defendsec/blob/v0.1.0/docs/INSTALL.md).

## Verify before you install

You should not have to trust us. Download the release files into an empty directory and run
`scripts/verify-release.sh` (from this tag) on them:

```bash
gh release download v0.1.0 --repo WASP512/defendsec --dir dl
curl -fL -o verify-release.sh \
  https://raw.githubusercontent.com/WASP512/defendsec/v0.1.0/scripts/verify-release.sh
bash verify-release.sh --strict --reproduce --tag v0.1.0 dl
```

It checks, in order: every file against `SHA256SUMS`; the Sigstore signature on `SHA256SUMS`
against this repository's release workflow, run on a tag; the GitHub build-provenance attestation
(shipped in the release as `SHA256SUMS.intoto.jsonl`, so no GitHub login is needed); and, with
`--reproduce`, a rebuild from source that must match the published Go binaries byte for byte. It
needs `cosign`, `gh` and Go for the checks that use them, and says plainly which check it could
not run. The CycloneDX SBOM of every binary and of the console is in the release.

## What is verified, and what is not

Everything below is from [docs/VERIFIED.md](https://github.com/WASP512/defendsec/blob/v0.1.0/docs/VERIFIED.md),
which lists the command and output behind each claim.

**Run on real hosts (two lab VMs):**

- Matching on a fully patched Ubuntu 22.04: 0 findings. On a fully patched Rocky 9.8: 0 fixable
  findings; 8 kernel CVEs that Red Hat has fixed and Rocky has not yet shipped are shown as
  `awaiting_vendor`.
- Real feed syncs of every default feed, ranking and the Fix this week card on real findings,
  application end-of-life and repository-health findings through a real server and agent, and the
  evidence round trip through `defendsec-verify`, including tampered bundles.
- Removing the EDR half: an old agent keeps working against the new server, and an old server
  database upgrades in place.

**Not run against the real thing. Treat as experimental:**

- The **Windows agent and MSI**: cross-compiled and parse-checked only; never run on a Windows
  machine.
- The **Datto RMM collector**, **Microsoft 365 identity posture** and **Autotask tickets**:
  tested against fakes and fixtures; no real account or tenant has been used.
- Application end-of-life and repository health on distributions other than Ubuntu 22.04 and
  Rocky 9.8; Debian, Fedora, Alma and openSUSE paths have unit tests but no real host.
- The external scanner has one vantage point and has been run on test domains only.

## Known issues

- Alert forwarding carries alerts only: not the audit ledger, surface, Microsoft 365 or
  repository-health findings.
- `docs/ROADMAP.md` and the technical white paper still describe removed features.
- A host that an old agent had isolated needs manual clean-up after an agent upgrade.
- The server keeps the fleet in memory; the figure of about 1.9 GB at 10,000 hosts is from an
  earlier version and has not been re-measured.
